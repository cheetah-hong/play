00이 문서는 무엇인가

이 매뉴얼은 방법론만 담습니다. 특정 언어·프레임워크·도메인 지식은 들어 있지 않으므로, 그대로 다른 프로젝트에 복사해 쓸 수 있습니다.

담고 있는 것

  • 세션이 끊겨도 맥락이 이어지는 문서 3층 구조
  • 테스트를 정본으로 고정하는 동결 TDD
  • 통과 못 하면 다음으로 못 가는 게이트 사다리
  • 서로 모르게 훑고 서로 반박시키는 리뷰 3단계
  • 에이전트가 침묵할 때의 회수 절차
  • orca·외부 CLI를 사람이 볼 수 있게 돌리는 법
  • 비개발자가 읽고 결정하는 보고서 형식

담지 않은 것

  • 언어·프레임워크별 코딩 규칙 프로젝트가 정함
  • 빌드·테스트 도구 설정 스택별
  • 도메인 지식·비즈니스 규칙 프로젝트가 정함
  • 배포 인프라 상세 환경별

이것들은 프로젝트의 CLAUDE.md 하단 「작업 원칙」 절에 각자 적습니다. 이 매뉴얼은 그 위쪽 절반을 제공합니다.

이 방식의 전제

사람은 오케스트레이터이고, 모델이 실행자다. 그래서 규칙 대부분이 「모델이 무엇을 못 보는가」와 「사람이 무엇을 못 보게 되는가」를 막는 데 쓰입니다. 코딩 규칙보다 가시성·검증·인수인계에 무게가 실려 있는 것은 그 때문입니다.

015분 도입 — 새 프로젝트에 얹기

저장소 루트에 파일 3개를 만든다
CLAUDE.md(규칙) · MEMORY.md(상태) · .gitignore. §16의 템플릿을 복사하고 「작업 원칙」 절만 프로젝트에 맞게 채웁니다.
디렉터리 3개를 만든다
plan/(일정) · sessions/(작업 기록) · briefing/(보고서). 비어 있어도 만들어 둡니다 — 있으면 채워집니다.
day-report 스킬을 넣는다
.claude/skills/day-report/SKILL.md. 보고서 형식을 매 세션 컨텍스트에 상주시키지 않으려고 스킬로 분리한 것입니다.
이슈 트래커에 작업 단위를 등록한다
Day 단위(또는 스프린트 단위) 이슈 + 주차 마일스톤 + 트랙 라벨. 이슈가 태스크의 진실 소스이고 MEMORY.md는 그 요약입니다.
첫 세션에서 방법론을 확정하고 다시 협의하지 않는다
게이트 기준·커버리지 임계·리뷰어 배정을 Day 01에 정해 CLAUDE.md에 박습니다. 매일 재협의하면 그 자체가 비용입니다.
왜 첫날에 확정하는가

방법론을 열어 두면 모델이 매 세션 다르게 해석합니다. 어느 날은 테스트를 먼저 쓰고 어느 날은 나중에 쓰는 식으로 흔들리면, 산출물의 신뢰 수준이 날마다 달라져 사후 감사가 불가능해집니다. 규칙은 최적이 아니어도 일정한 것이 낫습니다.

02문서 3층 구조 — 무엇을 어디에 적는가

세션이 끊겨도 맥락이 이어지려면, 정보를 수명에 따라 나눠 담아야 합니다. 같은 파일에 섞으면 오래 갈 규칙이 그날 메모에 묻힙니다.

파일수명담는 것읽는 시점
CLAUDE.md
규칙		프로젝트 전체 번복하지 않을 규칙. 세션 프로토콜 · 개발 방법론 · 게이트 · 리뷰 배정 · 코딩 규칙 · 정본 우선순위 세션 시작 시 자동 로드
MEMORY.md
상태		현재 시점 지금 어디까지 왔나. 진행률 · 확정 사항 · 미결 · 사람이 해줄 일 · 함정 목록 세션 시작 시 가장 먼저
sessions/day-XX.md
기록		그날 다음 세션의 나에게. 한 일 · 결정 · 막힌 것 · 다음이 이어받을 것 직전 것만
briefing/day-XX-report.html
보고		그날 결정권자에게. 비개발자 어휘. 전후 대조 · 진전도 · 결정사항 · 남은 오류 사람이 읽음
plan/daily-plan.md
계획		프로젝트 전체 Day별 태스크 · 트랙 배분 · 미결 처리 기본값 · 리스크 오늘 범위 확인
세 문장 규칙

번복하지 않을 것은 CLAUDE.md에. 오늘 바뀔 것은 MEMORY.md에. 오늘만 의미 있는 것은 sessions/에.

판단이 서지 않으면 이렇게 묻습니다 — 「2주 뒤에도 참일까?」 참이면 CLAUDE.md, 아니면 MEMORY.md입니다.

MEMORY.md에 반드시 있어야 하는 절

절왜 필요한가
🚨 지금 사람이 해줘야 할 일
최상단 고정		 계정 발급·법무 검토처럼 모델이 못 푸는 것. 최상단에 없으면 사람이 놓치고, 다음 세션이 같은 것에 또 막힙니다.
진행 현황Day n/N · 완료분 · 다음 마일스톤. 한눈에 보이는 진행 막대 하나면 충분합니다.
확정 사항 (번복 금지) 결정과 근거·날짜를 함께. 근거가 없으면 다음 세션이 같은 논의를 다시 엽니다.
미결 + 구현 기본값 승인 안 난 것도 기본값으로 구현하고 승인만 받습니다. 멈추지 않는 것이 핵심입니다.
⚠️ 알아둘 것 (함정) 한 번 당한 함정. 인코딩·버전 조합·계산 기준처럼 모르면 반드시 다시 당하는 것만.
다음 세션이 이어받을 것가장 먼저 할 일 1~3개. 구체적으로.

03세션 시작·종료 프로토콜

Day별로 세션을 나눠 작업하면 모델의 기억은 매번 0에서 시작합니다. 프로토콜은 그 공백을 파일로 메우는 절차입니다. 하나라도 빠지면 다음 세션이 맥락을 잃습니다.

🟢 세션 시작 — 첫 3분

  1. MEMORY.md 읽기 — 어디까지 왔나, 뭐가 막혔나
  2. 오늘 범위 확인 — plan/에서 오늘 Day와 태스크
  3. 이슈 확인 — 열린 이슈 목록, 오늘 것 파악
  4. 직전 세션 로그 — 「다음이 이어받을 것」 절만
  5. 착수 표시 — 이슈에 코멘트 또는 in-progress 라벨
  6. 방법론 절 재확인 — 매일 재협의하지 않고 그대로 적용
  7. 작업 표면 상태 갱신 — orca 워크트리 in-progress

🔴 세션 종료 — 빠짐없이

  1. sessions/day-XX.md — 개발 기록
  2. briefing/day-XX-report.html — 사람이 읽을 보고서
  3. MEMORY.md 갱신 — 진행률·확정·미결
  4. 이슈 처리 — 완료분 닫기, 진행분 코멘트, 신규 발견분 생성
  5. 커밋 & 푸시 — 컨벤션 준수
  6. 인프라 요청 정리 — 사람이 할 일을 MEMORY 최상단에
  7. 작업 표면 상태 갱신 — completed
  8. 원격 브랜치 정리 — 머지된 것만
7항·8항이 왜 따로 있나

초기에 이슈는 닫혔는데 작업 표면 UI는 착수 전으로 남는 일이 있었습니다. 사람이 보는 화면과 실제 상태가 갈리면, 사람은 진행 상황을 파일을 열어봐야만 알 수 있게 됩니다. 상태 갱신은 작업의 일부이지 부가 작업이 아닙니다.

브랜치 정리 — 열린 PR이 딸린 브랜치는 절대 지우지 않는다

지우면 그 PR이 자동으로 닫힙니다. 삭제 전 열린 PR 목록을 먼저 확인하십시오. 또한 존재하지 않는 ref가 하나라도 섞이면 push 전체가 원자적으로 거부됩니다 — 실측 목록(git ls-remote --heads origin)으로 실재하는 것만 넘깁니다.

지우는 것은 원격뿐입니다. 로컬 브랜치·워크트리·세션 기록은 건드리지 않습니다.

04날짜·기록 규칙 — 계획일과 수행일을 섞지 않는다

여유가 되면 작업을 앞당겨 하게 됩니다. 그러면 「Day 08」이라는 논리적 순서와 「8월 11일」이라는 실제 수행일이 갈라집니다. 이걸 섞으면 사후 감사가 막힙니다.

세 가지만 지킨다

① 문서 제목에 병기한다 — # Day 08 (계획 8/12 수 · 실제 수행 2026-08-11 화)

② 실제 수행일은 시스템 날짜로 얻는다 — date '+%Y-%m-%d (%a)'. 계획표를 보고 적지 않습니다.

③ 의심스러우면 데이터에 묻는다 — 산출물에 실행 시각이 박히는 필드가 있으면 거기서 역산해 확인합니다. 문서보다 데이터가 정확합니다.

★ 코드 일정은 앞당겨도 되지만, 달력에 묶인 작업은 앞당기면 안 된다

정기 배치·스냅샷 수집처럼 「실행 시각」 자체가 데이터가 되는 작업이 있습니다. 이런 것은 앞당기면 그 주의 관측이 영영 생기지 않습니다 — 소급 복원이 불가능합니다.

구현을 하루 앞당기는 것과, 거기 딸린 정기 실행을 앞당기는 것은 완전히 다른 결정입니다. 프로젝트에 이런 작업이 있으면 CLAUDE.md에 예외로 명시하십시오.

워크트리·브랜치 이름이 계획일로 만들어져 있어도 이름은 바꾸지 않습니다 — 식별자일 뿐입니다. 기록·보고서에만 실제 수행일을 적습니다.

05핸드오프 — 다음 세션을 위한 시작 프롬프트

세션 종료 시 sessions/day-XX.md와 별도로, 다음 세션이 그대로 읽고 시작할 프롬프트를 남기면 착수 시간이 크게 줄어듭니다.

sessions/day-NN-start-prompt.md
# Day NN 시작 프롬프트 (계획 M/D · 실제 수행 예정 YYYY-MM-DD)

> Day NN-1(요약, 이슈 #N, PR #M 머지) 완료에서 넘어온 핸드오프.
> 새 세션은 이 문서 + MEMORY.md + CLAUDE.md「세션 시작 프로토콜」을 먼저 읽는다.
> ⚠️ 실제 수행일은 `date '+%Y-%m-%d (%a)'` 로 확정해 병기한다.

## 오늘 범위
- 태스크 목록 (이슈 번호와 함께)
**DoD 감각**: 무엇이 되면 오늘이 끝난 것인가 — 한 문장

## ★ 착수 전 확정할 결정 N건
| # | 주제 | 권장 |
(직전 보고서의 「결정사항」 절에서 가져온다. 착수 전에 물어 확정)

## 🔴 달력에 묶인 것 (코드 일정과 무관)
(정기 배치 등. 오늘 반드시 돌려야 하는 것 + 실행 명령)

## 직전에서 이어지는 것
- 완료된 것이 오늘 무엇의 재료가 되는지
- 머지된 PR이 무엇을 바꿔 놨는지

## 먼저 볼 것
- 파일 경로 · 이슈 목록 · 정본 문서 순위
「먼저 볼 것」이 핵심이다

새 세션은 저장소 구조를 모릅니다. 경로를 구체적으로 적어두면 탐색에 쓰는 시간이 사라집니다. 「관련 코드를 찾아보라」가 아니라 「이 파일들을 열어라」로 적으십시오.

06테스트 동결 TDD — 이 방식의 핵심 규칙

모델이 구현과 테스트를 둘 다 쓰면, 막혔을 때 테스트를 고쳐서 통과시키는 유혹이 생깁니다. 그러면 테스트는 더 이상 검증이 아닙니다. 이를 막는 것이 동결입니다.

① 테스트 작성 (RED)        ─ 최상위 모델. 이게 정본이다
② ★ 테스트 컴파일 먼저      ─ 컴파일 안 되는 테스트를 동결하지 않기 위해
③ 동결 선언                ─ 해시를 기록 (git hash-object 등)
④ 구현 (GREEN)             ─ 테스트만 보고 로직 작성
⑤ 리팩터                   ─ 테스트 불변
동결의 세 조항

동결 후 테스트 수정 금지. 실패하면 구현을 고칩니다.

테스트가 실제로 틀렸으면 고치지 말고 신고 → 사람 승인 + 변경 전후 해시 기록. 단 단언 강도를 낮추지 않는 기계적 오류(import 경로·타입 캡처 등)는 진행 후 기록으로 갈음합니다.

매 게이트에서 테스트 파일 개수와 해시를 대조합니다.

②번은 25분을 날리고 추가된 단계다

컴파일도 안 되는 테스트를 동결해 두고 구현에 들어갔다가, 나중에 테스트를 고쳐야만 하는 상황에 빠졌습니다. 동결은 「컴파일되는 테스트」에만 의미가 있습니다. 건너뛰지 마십시오.

★ 해시 대조가 실제로 사고를 잡은 사례

리뷰 에이전트가 진단용 프로브 파일을 테스트 디렉터리에 심어 커버리지를 8.35%p 부풀렸습니다 (보고 93.74% ↔ 실제 85.39%). 동결 해시 대조가 아니었으면 통과했을 겁니다.

그래서 모든 리뷰어 프롬프트에 이 문구를 넣습니다 — "테스트 디렉터리 아래 파일을 생성·수정·삭제하지 말 것. 진단이 필요하면 저장소 밖 스크래치에서 하라."

무엇을 테스트하는가

반드시 한다하지 않는다
비즈니스 로직 · 계산 · 도메인 불변식
보안(인증 전 분기) · 예외 → 상태코드 매핑
응답 계약(필드명·구조)		 getter/setter · DTO 매핑
프레임워크 배선·설정 클래스
프레임워크 자체 동작

커버리지를 채우려는 테스트는 금지합니다. 생성 코드는 분모에서 제외하되, 설정·보안 클래스는 커버리지 제외 대상이 아닙니다 — 보안 오설정이 최대 리스크라 게이트가 울려야 합니다.

07게이트 사다리 — 앞 게이트 없이 다음 없다

#게이트합격 기준
G0빌드빌드 성공 + 커버리지 임계 통과
G1계약테스트 전부 통과 + 동결 해시·파일 개수 대조 일치
G2스키마·마이그레이션깨끗한 환경에서 재생성 검증(CI). 로컬에 재현 환경이 없으면 PR 필수
G3리뷰교차 리뷰 완료, BLOCKER 0
G4인수이슈 DoD 충족 + 세션 종료 프로토콜 완료
실기동 검증을 게이트에 준하게 취급한다

테스트가 통과해도 실제로 띄워서 요청을 넣어 보면 다른 결함이 나옵니다. 초기에 테스트가 못 잡은 결함 2건을 실기동+호출로 잡았습니다. 테스트는 「의도한 것」을 검증하고, 실기동은 「빠뜨린 것」을 드러냅니다.

심각도는 셋으로만 나눕니다 — BLOCKER 즉시 수정(게이트 차단) · MAJOR 당일 수정 · MINOR 이슈 이월. 더 잘게 나누면 분류에 시간이 듭니다.

08루프 정책 — 3회를 넘기면 그건 신호다

게이트 실패 → 원인 분류
  ├ 구현 결함    → 로직만 수정, 테스트 불변, 재실행   (라운드 +1)
  ├ 테스트 결함  → 중단 · 신고 · 승인 대기            (라운드 소모 X)
  └ 환경 결함    → 환경 수정                          (라운드 소모 X)
→ 라운드 3 초과 → 중단 · 에스컬레이션 · push 금지
원인 분류가 먼저다

세 종류의 실패는 대응이 완전히 다릅니다. 분류 없이 재시도하면 테스트가 틀렸는데 구현을 계속 고치는 무한 루프에 빠집니다.

라운드를 소모하는 것은 구현 결함뿐입니다. 나머지는 애초에 다른 절차입니다.

게이트당 3회. 같은 실패를 3번 넘겨 반복하는 것은 진전이 아니라 「전제가 틀렸다」는 신호입니다. 그때는 사람에게 올립니다.

09모델·역할 배정

모든 작업에 최상위 모델을 쓰면 비용이 낭비되고, 모든 작업에 경량 모델을 쓰면 설계가 무너집니다. 판단이 필요한 곳에만 상위 모델을 씁니다.

역할배정이유
오케스트레이션 · 설계 · 테스트 명세 작성최상위 · 높은 추론 테스트가 정본이므로 여기가 가장 비싸야 합니다
뼈대 이식 · 보일러플레이트 · 스캐폴딩중간 모델 패턴 복제라 판단이 거의 없습니다
보안 관련 구현최상위 실수의 비용이 비대칭적으로 큽니다
1차 코드리뷰외부 모델 (codex 등) 모델 다양성 — 같은 모델은 같은 맹점을 가집니다
2차 교차 리뷰Claude 전문 리뷰 에이전트 언어별 관용구 · 공격자 관점
빌드 에러 해결중간 모델 기계적 수정

ECC(everything-claude-code) 플러그인 운용

리뷰·빌드 에이전트는 ECC 플러그인이 제공하는 것을 씁니다. 언어별 리뷰어 (*-reviewer)와 빌드 해결사(*-build-resolver)가 갖춰져 있어 스택이 바뀌어도 같은 역할 구조를 유지할 수 있습니다.

★ 이중 설치를 반드시 확인한다

ECC를 플러그인으로도 설치하고 ~/.claude/agents/에 사본으로도 두면 같은 에이전트가 두 벌 뜹니다. 그러면 이름 해석이 설치 형태에 따라 달라져, 어제 되던 호출이 오늘 안 됩니다.

사본을 걷어내고 플러그인 단독으로 두면 플러그인명:에이전트명 접두사형이 정본이 됩니다. 짧은 이름은 더 이상 해석되지 않으므로, CLAUDE.md에 접두사를 포함한 정확한 표기를 적어 두십시오.

사본 제거는 스킬 컨텍스트 예산도 함께 줄여줍니다 — 중복 스킬이 사라지기 때문입니다.

# 설치 형태 점검 — 사본이 0이어야 한다
ls ~/.claude/agents/ 2>/dev/null | wc -l
ls ~/.claude/plugins/
쓰지 않기로 한 것도 적어 둔다

플러그인이 제공하는 명령 중 의존 파일이 없어 실패하거나, 모델·설정이 하드코딩되어 프로젝트 규칙과 어긋나는 것이 있습니다. 「쓰지 않는 것」 목록을 CLAUDE.md에 이유와 함께 적어두면, 다음 세션이 그걸 다시 시도했다가 시간을 버리지 않습니다.

DAG 오케스트레이션처럼 지금 규모에 이득이 없는 기능도 마찬가지입니다 — 「의존성이 선형이라 디버깅 표면만 늘어난다. 트랙 3개가 동시에 물리면 재검토」처럼 재도입 조건까지 적습니다.

10★ 리뷰 3단계 프로토콜 — 이 방식의 가장 값진 자산

1단계 · 분업 탐색   각자 전문 영역을 독립 스윕   ★ 서로의 발견을 알려주지 않는다
2단계 · 교차 반증   상대 지적을 "반박해보라"      ★ "확인"이 아니라 "반증"
3단계 · 판정        수렴/충돌로 신뢰도 결정

1단계 — 분업 탐색 (절대 공유하지 않는다)

리뷰어전담 영역
외부 모델 codex 등 전체 diff 스윕 — 의존성 · 설정 · 스키마 · CI · 명세 위반
보안 리뷰어 공격자 관점 — 실제 기동해 우회 시도, 권한 · 누설 · fail-open
언어 리뷰어 언어·프레임워크 관용구 · 아키텍처 확장성 · 설계 부채
★ 2차 리뷰어에게 1차 결과를 알려주면 안 된다

「1차가 이걸 찾았다」고 알려주면 그걸 사실로 깔고 시작합니다. 그러면 독립 수렴이라는 가장 값진 신호가 사라집니다.

실제로 서로 모르는 두 리뷰어가 같은 MAJOR에 독립적으로 도달한 적이 있습니다 — 그게 「이건 진짜다」의 가장 강한 증거였습니다. 공유했으면 얻지 못했을 신호입니다.

2단계 — 교차 반증

프롬프트 문구를 그대로 쓴다

"이 지적을 반박해보라. 확신이 없으면 반박 성공으로 간주하라."

「확인하라」고 시키면 동의 편향이 걸립니다. 모델은 주어진 주장을 지지하는 근거를 찾는 쪽으로 기웁니다. 반박하라고 시켜야 실제 검증이 일어납니다.

BLOCKER·MAJOR에만 겁니다. MINOR까지 반증시키면 비용만 배가 됩니다.

3단계 — 판정

상황신뢰도처리
양쪽이 독립적으로 같은 지적최고즉시 수정
A 발견 → B 반증 실패높음수정
A 발견 → B 반증 성공낮음기각 + 근거 기록
A·B 의견 충돌—사람에게 양쪽 논거를 그대로 제시
마지막 줄이 이 표의 목적이다

충돌을 감추지 않고 드러내야 사람이 납득할 근거가 생깁니다. 모델이 임의로 한쪽을 골라 「해결했습니다」라고 보고하면, 사람은 무엇이 걸렸었는지 영영 모릅니다.

수렴이 곧 정답은 아니다

둘이 같이 틀릴 수도 있습니다. 독립 수렴은 강한 신호지만 증명은 아닙니다. 최종 심각도는 수렴한 리뷰어 수가 아니라 재현 가능성으로 정하십시오 — 「실제로 이 입력을 넣으면 이 결과가 나온다」를 확인할 수 있으면 그게 근거입니다.

11에이전트 회수 — 결과를 안 보낼 때

서브에이전트가 침묵하면 죽은 것인지 일하는 중인지 구별되지 않습니다. 서둘러 잘라내면 살아 있는 것을 죽이고, 무한정 기다리면 세션이 멈춥니다.

서브에이전트 프롬프트 필수 조항 3가지

"N분 내 진전이 없으면 즉시 보고하라"
구현 에이전트가 25분간 막힌 채 침묵한 적이 있습니다. 막혔다는 보고도 진전입니다.
"테스트 디렉터리를 건드리지 말 것"
리뷰어가 진단 파일을 심어 커버리지를 왜곡했습니다. 진단은 저장소 밖에서.
"평문 출력은 전달되지 않는다. 반드시 메시지로 메인에 보내라"
서브에이전트가 리포트를 텍스트로만 내고 끝내면 메인 세션에 아무것도 도착하지 않습니다. 이 형태는 에이전트가 죽은 것과 구별되지 않습니다.

미제출 시 회수 절차 — 최대 3회

① 판정 먼저 — 죽었나, 살아서 파악 중인가
   ├ 유휴 상태가 "available" · 진행 로그가 있다 · 명령이 정상 접수됐다 → 살아 있다. 기다린다
   └ 프로세스 없음 · 오류 종료 · 명령 자체가 안 들어갔다              → 그때만 재시작·폴백

② 재요청 최대 3회. 매 회차에 반드시 넣을 것
   · "평문 말고 메시지로 보내라"
   · "완성도 낮아도 괜찮다 / 조사 중이면 조사 중이라고만 보내라"
   · "문제 없으면 문제 없다고 보내라"  ← 이게 빠지면 침묵과 구별이 안 된다
   · 그사이 커밋이 얹혔으면 현재 상태와 무엇이 바뀌었는지 알려준다

③ 3회 모두 무응답 → 폴백. 모델 다양성 상실을 기록에 명시
서둘러 잘라내지 않는다 — 두 번 다 오판이었다

한 번은 60분 만에 잘랐는데 실제로는 살아 있었고, 회수 방법을 안 알려준 것이 원인이었습니다.

같은 날 외부 CLI도 스크롤백에 남은 옛 줄만 보고 정체로 오판해 인터럽트했는데, 실은 이미 최종 리포트를 출력하는 중이었습니다.

화면에 남은 옛 줄이 아니라 최신 출력으로 판정하십시오. 목록에서 사라진 것도 사망의 증거가 아닙니다 — 3회 재요청이 먼저입니다.

12orca 역할 분담 — 사람이 볼 수 있게 돌린다

orca와 Claude Code를 각자 강점에 맞게 나눠 씁니다. 한쪽으로 몰지 않습니다.

담당도구용도
워크트리 · 진행 상태 가시화orca orca worktree set --workspace-status {todo|in-progress|in-review|completed} · --comment · 트랙 분리 시 worktree create
에이전트 실행 · 컨텍스트 격리Claude Code 서브에이전트 툴 · 상태 확인 메시지
외부 모델 호출orca terminal orca terminal create --command "…" — Bash 백그라운드 금지
산출물(HTML) 띄우기orca 브라우저 탭 orca tab create --url "file:///…" — OS 기본 열기 금지
파일 열기 · difforca 편집기 orca file open · orca file diff
단 하나의 원칙

사람이 지켜봐야 할 장시간 작업을, 사람이 못 보는 곳에서 돌리지 않는다.

Claude 서브에이전트는 하네스가 UI에 띄워 줍니다. 그런데 외부 CLI만 Bash 백그라운드로 돌리면 출력이 파일에만 쌓여 화면에서 사라집니다 — 다른 에이전트는 다 보이는데 그것만 깜깜이가 됩니다.

브라우저 탭 — OS 기본 열기를 쓰지 않는 이유

macOS open 등을 쓰면 orca 밖 기본 브라우저로 열려 맥락에서 떨어지고, orca가 기본 브라우저면 탭이 중복 생성됩니다. 만든 뒤에는 목록으로 확인하고 중복은 닫으십시오.

# 세션 시작
orca worktree set --worktree active --workspace-status in-progress --comment "Day XX 착수 — 요약"
# 산출물 띄우기 (--focus 는 붙이지 않는다)
orca tab create --worktree active --url "file:///$(pwd)/briefing/day-XX-report.html" --json
orca tab list --worktree active          # 중복이면 orca tab close --page <id>
# 세션 종료
orca worktree set --worktree active --workspace-status completed --comment "Day XX 완료 — PR #N"

13외부 리뷰 CLI 운용 — 실측으로 얻은 함정들

외부 모델 CLI(codex 등)를 리뷰어로 쓸 때 겪은 것들입니다. 도구가 달라도 같은 성질의 함정이 재현되므로 점검 목록으로 쓰십시오.

★ headless(exec)가 아니라 대화형 TUI로 띄운다

exec 계열은 원시 로그만 쏟아져 다른 에이전트 탭과 보이는 방식이 전혀 다릅니다. 대화형으로 띄우면 탭으로 보이고, 중간 출력을 읽을 수 있으며, 포그라운드 시간 제한도 받지 않습니다.

실측으로 headless는 양일 모두 정체해 최종 리포트를 못 냈고, TUI는 정체 없이 완주했습니다.

함정대응
기본이 무제한 권한으로 뜬다 읽기 전용 샌드박스를 명시합니다. 리뷰어에게 쓰기 권한을 주지 않습니다 — 진단 파일을 심어 커버리지를 왜곡한 전례가 있습니다.
모델이 기본값으로 뜬다 모델과 추론 강도를 반드시 명시합니다. 안 주면 규칙과 다른 모델이 리뷰합니다.
읽기 전용에서 조회 명령이 막힌다 임시 캐시 접근 때문에 승인 프롬프트가 뜹니다. 접두사째 허용으로 넘기되 샌드박스 자체는 읽기 전용을 유지합니다. 조회 계열이라 허용 범위가 좁습니다. 리뷰어가 권한 때문에 멈춰 있는 것은 진전이 아닙니다.
읽기 전용은 네트워크도 막는다 CI 결과를 조회하려다 멈춥니다. CI 결과는 프롬프트에 직접 넣어 줍니다.
유휴 감지로 완료를 판정하면 안 된다 중간 유휴에 걸려 조기 반환합니다. 화면에서 「중단하려면 esc」 류 표시가 사라졌는지로 판정합니다.
첫 기동 시 업데이트 프롬프트건너뛰기 응답을 보내 넘깁니다.
스피너 잔상이 섞인다공백 압축 + 정규식으로 걷어내고 읽습니다.
핸들과 ID를 혼동하지 않는다

터미널을 만들면 반환값에서 후속 조작에 쓰는 키를 정확히 뽑아야 합니다. ID처럼 보이는 필드가 여러 개일 때 잘못 잡으면 이후 명령이 전부 실패합니다. 한 번 확인해 CLAUDE.md에 적어 두십시오.

14보안 · 자격증명 · 기록 표기

자격증명

  • 시크릿은 환경변수로만. .env는 커밋 금지
  • 비밀번호를 셸에 직접 치거나 대화에 붙여넣지 않는다 — 히스토리·기록에 남는다
  • 파일에서 읽어 환경변수로 올린다
  • 자격증명을 전역 설정 파일에 두지 않는다 — 백업본에도 딸려간다
  • 워크트리별 .env는 gitignore되므로 새 워크트리에 복사가 필요하다

기록 표기

  • 커밋·PR에 도구 관련 표기를 넣지 않는다
  • 저장소 기록에는 작업자 계정만 남는다
  • 커밋 컨벤션 준수 (feat:/fix:/docs:/chore:)
  • git 신원을 일관되게 고정한다 — 이메일이 갈리면 같은 사람의 커밋이 둘로 세어진다
외부 데이터·API는 약관을 먼저 본다

공개돼 있다고 자유롭게 쓸 수 있는 것이 아닙니다. 저장 금지·재배포 조건·상업적 이용 제한이 걸려 있으면 설계 자체가 달라집니다(예: 저장 금지 조항이면 캐시 대신 실시간 조회로 가야 합니다).

연동 착수 전에 확인하십시오. 구현을 마치고 발견하면 그 작업이 통째로 버려집니다.

15비개발자 보고 체계

개발 기록과 보고서는 독자가 다르므로 하나로 합치지 않습니다. sessions/day-XX.md는 다음 세션의 나에게, briefing/day-XX-report.html은 읽고 결정을 내리는 사람에게 갑니다.

보고서에 반드시 담을 5개 절

#절내용
1작업 전 / 작업 후나란히 대조. 무엇이 없었고 무엇이 생겼는지
2전체 진전도Day n/N · 다음 마일스톤 · 핵심 수치 타일
3발견 / 검증조사로 뒤집힌 전제 · 게이트 결과
4결정사항사람이 정할 것. 선택지 + 권장안 + 각 선택의 비용을 함께
5남은 오류·미검증이월 이슈 + 「언제 문제되나」를 반드시 함께
4절과 5절이 보고서의 존재 이유다

결정사항을 「정해주세요」로 끝내지 않습니다. 선택지 A·B, 권장안 표시, 각 선택의 비용을 적어야 그 자리에서 정할 수 있습니다.

남은 오류는 「언제 드러나는지」가 핵심입니다. 「지금은 무해하지만 배포 시점에 터진다」까지 적어야 우선순위를 정할 수 있습니다.

작성 원칙

### 테스트 동결 TDD
① 테스트(RED) → ② 테스트 컴파일 확인 → ③ 해시 동결 → ④ 구현(GREEN) → ⑤ 리팩터

- 매 게이트에서 테스트 파일 개수·해시 대조

### 게이트 사다리
G0 빌드+커버리지 / G1 테스트+해시대조 / G2 스키마 재생 / G3 리뷰 BLOCKER 0 / G4 인수
- 실기동 검증을 게이트에 준하게 취급한다

### 루프 정책
실패 → 원인 분류(구현/테스트/환경) → 구현 결함만 라운드 소모 → 3회 초과 시 중단·에스컬레이션

### 모델 배정
오케스트레이션·설계·테스트명세 = 최상위 / 스캐폴딩 = 중간 / 보안 = 최상위
1차 리뷰 = 외부 모델 / 2차 = 전문 리뷰 에이전트 / 빌드에러 = 중간
⚠️ 에이전트 이름 정확한 표기: <플러그인명>:<에이전트명>

### 리뷰 3단계
1단계 분업 탐색 (★서로의 발견을 공유하지 않는다)
2단계 교차 반증 ("이 지적을 반박해보라. 확신 없으면 반박 성공으로 간주하라")
3단계 판정 (독립 수렴=최고신뢰 / 충돌=사람에게 양쪽 논거 제시)
- 리뷰어 프롬프트에 "테스트 디렉터리를 건드리지 말 것" 필수
